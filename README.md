# ticket-pulse

A multi-agent pipeline that ingests multilingual customer support tickets,
translates and classifies them, detects temporal anomalies in per-category
ticket volume, and synthesizes a grounded daily triage report — entirely
with local, no-login models and public data.

See [DESIGN.md](DESIGN.md) for the architecture and every design decision,
and [LEARNING.md](LEARNING.md) for the real bugs hit building it (including
one that silently corrupted output files for several test runs) and how
they were found and fixed — written to be defensible in an interview, not
just a changelog.

## Status: all phases built, tested, and run end-to-end with real numbers

Real run (`run1`, local OS processes — one per agent, all communicating
over a real Redis broker; not `docker compose` for this particular run, see
"A note on how this was run" below) against 1,676 synthetic tickets across
35 simulated days (`data/synthetic/`, generated by
`scripts/generate_tickets.py` from real multilingual utterances — see
[Data](#data)):

```
Translation quality (back-translation consistency, 309-ticket sample):
  mean=0.698  median=0.714  p10=0.444
  (weakest: zh-CN 0.598, ar 0.602 -- strongest: pt 0.789, es 0.779)

Classification (zero-shot, bart-large-mnli):
  scenario taxonomy (real labels):    accuracy=0.424  macro-F1=0.417
  custom taxonomy (silver mapping):   accuracy=0.473  macro-F1=0.457
  hard/ambiguous subset (48 examples): accuracy=0.333

Anomaly detection vs. 3 injected windows (8 known anomalous category-days):
  CUSUM (default, threshold_std=3.5):    precision=0.077  recall=0.25  f1=0.118
  Poisson-rate (default, alpha=0.01):    precision=0.667  recall=0.25  f1=0.364
  Poisson-rate (tuned, alpha=0.005):     precision=1.00   recall=0.25  f1=0.400  (0 false positives)
```

35/35 daily reports generated, all via the real local Ollama model (no
template fallbacks needed in this run). 21 unit/integration tests passing.

**These numbers tell a real, traceable story, not just "the model is
inaccurate" — see [Evaluation](#evaluation) for the root-cause analysis**:
classification accuracy is the actual bottleneck on anomaly recall, and the
two detectors, run head-to-head on the same data, are *not* close —
Poisson-rate clearly wins for this kind of sparse per-category count data,
exactly as [DESIGN.md](DESIGN.md) predicted before either was measured.

## A note on how this was run

The Dockerfile and `docker-compose.yml` are real and complete (5 agent
services + Redis + Ollama, see [DESIGN.md](DESIGN.md)), but the run whose
numbers are reported above used local OS processes against a native
Homebrew Redis instead of the full `docker compose` stack. This was a
deliberate call, not a shortcut: mid-build, running all 4 model-loaded
agents as separate long-lived processes pushed the host to 18.3GB/19.4GB
swap used and the machine started thrashing, on top of Docker Desktop's own
VM overhead (~8GB resident) and other applications already running. See
LEARNING.md #3. `make demo` (the containerized path) works the same way
architecturally — same code, same Redis protocol, same 5 separate
processes — just wasn't the execution path used to produce these numbers
on this particular machine.

## Quickstart

```bash
make venv      # local Python env
make fixture   # generates data/synthetic/{tickets.jsonl,ground_truth_anomalies.json,hard_examples.jsonl}
make test      # 21 fast tests, no models downloaded
```

To reproduce the real run (downloads ~1.9GB m2m100 + ~1.6GB bart-large-mnli
from the public HF Hub on first use, no token needed; needs a local Ollama
with a model pulled, e.g. `ollama pull qwen2.5:3b-instruct`):

```bash
# containerized (the architecturally "real" path):
make demo

# OR, if RAM is tight (see "A note on how this was run" above):
redis-server --port 6379 --daemonize yes     # or `brew install redis` first
bash scripts/run_local_demo.sh run1 data/synthetic/tickets.jsonl 0.05
.venv/bin/python eval/run_eval.py --run-id run1
```

`scripts/run_local_demo.sh` starts all 4 long-lived agents as separate
local processes, streams `tickets.jsonl` in via `ingestion_agent` at a
simulated day cadence (`0.05` wall-clock seconds/day here; the tickets
themselves carry real simulated timestamps regardless of this), and waits
for the final day's report. Real per-ticket cost on this machine was
CPU-bound on classification (~3-5s/ticket, bart-large-mnli scoring 2
taxonomies); the full 1,676-ticket run took about 90 minutes.

## Architecture

Five agents, five separate OS processes, communicating only through Redis
lists — never a shared in-memory object:

```
ingestion_agent → translation_agent → classification_agent → anomaly_agent → synthesis_agent
  (one-shot run       (m2m100_418M,        (bart-large-mnli          (CUSUM +           (Ollama,
   trigger)             sampled back-        zero-shot,               Poisson-rate         grounded in
                        translation          2 taxonomies)            tests)               exact counts)
                        check)
```

Full data flow, the day-boundary barrier pattern, and why classification
runs against two label sets per ticket are in [DESIGN.md](DESIGN.md).

## Data

No real, no-login support-ticket dataset exists, so this project generates
a **synthetic ticket stream** (as the build spec itself recommends when
that's the case): real multilingual utterances from `mteb/amazon_massive_scenario`
(a public, no-login Parquet mirror of Amazon's MASSIVE corpus — the
originally-suggested `AmazonScience/massive` dataset no longer loads with
current `datasets` versions, see LEARNING.md #1) sampled onto a 35-day
timeline across 8 locales (en, es, fr, de, hi, ar, zh-CN, pt) and 18
categories, with 3 deliberately injected volume-anomaly windows of
different difficulty:

| category  | days  | multiplier | detected? |
|-----------|-------|------------|-----------|
| iot       | 10-13 | 5.0x       | no (see root-cause analysis below) |
| weather   | 22-23 | 6.0x       | **yes**, both days, both methods |
| transport | 29-30 | 2.5x       | no (deliberately the "weak" case) |

Exact ground truth: `data/synthetic/ground_truth_anomalies.json`.

## Evaluation

`eval/run_eval.py --run-id <id>` reads only files a run leaves behind
(`reports/<run_id>/tickets_scored.jsonl`, `day_counts.csv`) plus the
synthetic ground truth — never touches Redis, works the same against a
live or a saved run. Full output: `reports/run1/eval_results.json`.

### Translation quality

Back-translation consistency (translate to English, then back to the
source language, score similarity against the original) over a **held-out
sample** of 309 non-English tickets — not every ticket, since the eval
spec only asks for this metric on a sample and it doubles translation cost;
see `config.BACK_TRANSLATION_SAMPLE_RATE` and LEARNING.md #4.

| locale | mean similarity |
|--------|------------------|
| pt     | 0.789 |
| es     | 0.779 |
| fr     | 0.741 |
| de     | 0.719 |
| hi     | 0.680 |
| ar     | 0.602 |
| zh-CN  | 0.598 |

Romance languages round-trip best through m2m100_418M; Arabic and
Mandarin — the two most structurally distant from English among the
sampled locales — round-trip worst. This matches the model's known
strengths (it's stronger on the language pairs best-represented in its
training data) rather than indicating a pipeline bug.

### Classification: two taxonomies, and a real, traced failure mode

Zero-shot classification (`facebook/bart-large-mnli`) against MASSIVE's own
18-scenario taxonomy scored **42.4% accuracy / 41.7% macro-F1** against real
labels. Against this project's own invented 7-category support-desk
taxonomy (scored against a silver-standard mapping, not a human label —
see `classification_agent/taxonomy.py`), **47.3% accuracy / 45.7% macro-F1**.

That's mediocre for 18 classes, but it isn't uniform, and the *shape* of
the errors is the interesting part:

```
category        n     accuracy   most-confused-with
email           151   0.74       (correctly self-classified)
transport        68   0.76       (correctly self-classified)
alarm            65   0.72       (correctly self-classified)
weather         148   0.53       (correctly self-classified)
...
general         153   0.15       -> recommendation (49 of 153)
qa              141   0.06       -> recommendation (59 of 141)
iot              98   0.01       -> recommendation (56 of 98)
cooking          31   0.29       -> recommendation (19 of 31)
music           115   0.17       -> audio (69 of 115)
play             98   0.17       -> audio (46 of 98)
```

**"recommendation" and "audio" act as sink labels**: the model over-predicts
them for anything even loosely adjacent (372 "recommendation" predictions
against only 73 true instances), which is *why* `iot` has essentially 0%
recall — almost every real iot ticket ("turn on the lights") gets
classified as "recommendation" instead. The hard/ambiguous-examples set
(48 examples deliberately sampled from confusable scenario groups —
datetime/calendar/alarm, music/audio/play, qa/general/news,
recommendation/cooking/takeaway) scores **33.3% accuracy**, meaningfully
below the 42.4% overall average, confirming the harness is actually
measuring the failure mode it was built to find, not just an average.

This wasn't fixed (out of scope for this build — a better hypothesis
template, per-category calibration, or a larger NLI model are the obvious
next things to try), but it's the reason the anomaly-detection recall below
looks worse than the detectors' own math deserves.

### Anomaly detection: the detectors work; classification noise hides two of three signals

`eval/run_eval.py` sweeps both detectors across a range of thresholds
against the 3 injected windows (8 true anomalous category-days total) and
reports the full precision/recall/false-positive-rate tradeoff, not one
cherry-picked point — full sweep in `reports/run1/eval_results.json`,
plotted in `reports/run1/threshold_sweep.png`.

| method   | threshold | precision | recall | f1    | fp | fpr    |
|----------|-----------|-----------|--------|-------|----|--------|
| CUSUM    | 1.5 (loosest) | 0.024 | 0.25 | 0.043 | 82 | 0.132 |
| CUSUM    | 3.5 (configured default) | 0.077 | 0.25 | 0.118 | 24 | 0.039 |
| CUSUM    | 4.0 (best F1 in sweep) | 0.080 | 0.25 | 0.121 | 23 | 0.037 |
| Poisson  | 0.20 (loosest) | 0.036 | 0.375 | 0.066 | 80 | 0.129 |
| Poisson  | 0.01 (configured default) | 0.667 | 0.25 | 0.364 | 1 | 0.0016 |
| Poisson  | 0.005 (best F1 in sweep) | **1.00** | 0.25 | **0.400** | **0** | **0.0** |

**CUSUM never gets above 12% precision at any threshold tested** — this
per-category ticket-count data is too sparse and too zero-inflated (several
categories average under 1 ticket/day) for a std-dev-based detector; it
mistakes ordinary Poisson noise on a low-volume category for a mean shift,
repeatedly (e.g. the `lists` category alone was falsely flagged on 3
separate days). **Poisson-rate, at a stricter alpha, gets perfect precision
with zero false positives** — exactly the outcome [DESIGN.md](DESIGN.md)'s
architecture section predicted before either was measured ("ticket counts
are a counting process ... meaningful even at small per-category daily
counts where a std-dev-based test is noisy"). Recommendation: use
Poisson-rate as the primary detector; CUSUM's value here is mostly
pedagogical (showing the comparison), not operational.

**Why recall caps at 0.25 (2 of 8) regardless of threshold**: tracing the
two undetected windows against the *true* injected data (not the
classifier's predictions) shows the injected spikes are genuinely there —
39 true `iot` tickets landed in the days 10-13 window, a clear 5x spike —
but the classification failure mode above means the anomaly agent (which,
correctly mirroring a real production system, only ever sees *predicted*
categories) never saw an `iot` spike: it saw a `recommendation` spike
instead, indistinguishable from that category's already-noisy baseline.
The `weather` window survived because its 6x multiplier and comparatively
good 53% classification accuracy left a strong enough signal to clear the
noise floor even after dilution. `transport`'s window was the intentionally
weak case (2.5x on an already-noisy baseline) and wasn't expected to be
reliably caught. **This is a real, traced coupling between pipeline
stages** — anomaly-detection recall is bounded above by classification
recall on the affected category — not three independent failures.

## Tests

```bash
make test   # 21 tests: CUSUM + Poisson detector math (including a
            # known-injected-spike detection test and a false-positive-rate
            # check on flat series), translation/classification input-output
            # contracts (mocked models), Redis broker round-trip (fakeredis),
            # and a full in-process end-to-end flow with an injected spike
            # verified to reach a grounded report
```

No `pytest -m slow` tier here (unlike repo-health-radar) — every model call
in this pipeline is mocked out in tests; the real models are only ever
exercised by an actual run (`make demo` / `run_local_demo.sh`) plus
`eval/run_eval.py`.
